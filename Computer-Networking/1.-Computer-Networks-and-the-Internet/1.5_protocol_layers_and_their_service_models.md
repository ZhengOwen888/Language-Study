# 1.5 - Protocol Layers and Their Service Models

> **Big Idea:** The Internet is incredibly complex. To manage that complexity, it protocols are organized into **layers** - each layer handles one specific job and relies on the layer below it to handle the rest.

---

## 1.5.1 Layered Architecture

### The Airline Analogy

Think about everything that happens when you fly: buying a ticket, checking bags, boarding at the gate, takeoff/landing, and the plane being routed through the sky. Each of these can be though of as its own **layer**:

| Layer (top->bottom) | What it handles |
|---|---|
|Ticketing | Counter-to-counter transfer a person (purchase / complain) |
| Baggage | Check-to-claim transfer of bags (only for already-ticketed, already-baggage-checked people) |
| Takeoff/Landing | Runaway-to-runaway transfer |
| Airplane Routing | Getting the plane through the sky to the right airport |

> **Key insight:** Each layer only needs to worry about ITS job, and trusts the layer below to handle everything beneath it. The ticketing layer doesn't care HOW the plane gets routed - it just uses the service the lower layers provide.

### Why Layering? (Advantages)
- **Modularity:** You can change HOW a layer worksinternally (its *implementation*) without breaking anything else, AS LONG AS it still provides the same service to the layer above it and still uses the same services from the layer below.
- Make discussing/designing a hugely complex system (like the Internet) much more manageable.

### Downsides of Layering (yer, there are some!)
- A layer might **duplicate** functionality that another layer already does (e.g., error-recovery being done at both the link layer AND end-to-end).
- Sometimes a layer needs info that only exists in a DIFFERENT layer (like a timestamp) - this breaks the clean seperation  between layers.

### The Internet Protocol Stack - 5 Layers

> When you stack all the protocols from every from layer together, it's called the **protocol stack**.

| Layer (top -> bottom) | Job | Key Protocols | Data unit name |
|---|---|---|---|
| **Application** | Where network apps and their protocols live - this is what end-user programs actually use | HTTP (web), SMTP (email), FTP (file transfer), DNS (name lookup) | **Message** |
| **Transport** | Transports application-layer messages between the two end applications | **TCP** (reliable, connection-orientied) and **UDP** (unreliable, connectionless, no-frills) | **Segment** |
| **Network** | Moves packets (datagrams) from one HOST to another, across the whole path | **IP** (the "glue" of the Internet - only one IP protocol exists) + various routing protocols | **Datagram** |
| **Link** | Moves a datagram from one NODE to the next adjacent node (one hop) | Ethernet, Wi-Fi, DOCSIS (cable), PPP | **Frame** |
| **Physical** | Moves the individual BITS within a frame from one node to the next, over the actual physical medium | Different for each medium (twisted-pair, fiber, coax, etc.) Bits |

### Key Vocabulary

| Term | Simple Definition |
|---|---|
| **TCP** | Connection-oriented transport protocol - guarantees delivery, does flow control (matches send or/receiver speed), breaks big messages into segments, does congestion control. |
| **UDP** | Connectionless transport protocol - no guarantees, no flow control, no congestion control, "No-frills". |
| **IP (Internet Protocol)** | The single, universal network-layer protocol that defines datagram format and how routers/hosts act on it. Sometimes the whole network layer is just called "the IP layer". |
| **Routing protocol** | Determine the actual PATHS datagrams take (different from IP itself, which just defines the datagram format). |

> **Important distinction:** The link layer's "reliable delivery" (if a link-layer protocol offers it) is different from TCP's reliable delivery - link-layer reliability only covers ONE hop/link, while TCP's reliability covers the ENTIRE end-to-end path.
> A single datagram may be handled by DIFFERNT link-layer protocols on different links along its journey (e.g., Ethernet on one hop, PPP on the next) - the network layer gets a differnt "service" from each one.

## 1.5.2 Encapsulation

> **Encapsulation** = each layer takes what irt receives from the layer above and wraps it with its OWN header information, creating a new (larger) unit to pass down to the next layer.

### The Encapsulation Chain (top -> bottom, at the SENDER)

| Layer | What happens | Resulting unit |
|---|---|---|
| Application | Creates the data | **Message (M)** |
| Transport | Adds transport header (`Ht`) | **Segment** = `Ht + M` |
| Network | Adds network header (`Hn`) | **Datagram** = `Hn + Ht + M` |
| Link | Adds link header (`H1`) | **Frame** = `Hl + Hn + Ht + M` |

> Every layer's unit has **2 parts**: a **header** (that layer's own control info) and a **payload** (whatever was handed down from the layer above - usually the ENTIRE unit from the layer above).

At the **receiving end**, this happens in REVERSE - each layer strips off (removes) its corresponding header as the data moves back UP the stack. This reverse process is called **de-encapsulation**.

### The Interoffice Memo Analogy

| Networking Concept | Memo/Mail Equivalent |
|---|---|
| Application-layer Message (M) | The actual memo Alice writes. |
| Transport-layer Segment | The interoffice envelope (has Bob's name and dept written on it = header info) wrapping the memo. |
| Network-layer Datagram | The OUTER postal envelope (has full postal addresses = header info) wrapping the interoffice envelope. |
| De-encapsulation at the destination | The receiving mailroom opens the postal envelope, pulls out the interoffice envelope, delivers it to Bob, who then opens it and reads the memo. |

### Which Devices Implment Which Layers?

> **Important exam fact:** Not every device implement ALL 5 layers:

| Device | Layers it implements | Why |
| **Host (end system)** | ALL 5 layers (Application -> Physical) | Hosts run the actual applications and need the full stack. |
| **Router** | Layers 1-3 (Physical, Link, Network) | Routers need the Network layer to read IP addresses and decide where to forward packets - but don't need Tarnsport/Application |
| **Link-layer Switch** | Layers 1-2 (Physical, Link) ONLY | Switches only need to read link-layer (e.g., Ethernet) addresses - they can't even see/understand IP addresses! |

> **Why this matters:** This is WHY link-layer can't route based on IP address (they don't implement the Network layer at all) but routers can - routers "see" one layer higher than switches do.

## Quick Review — Key Takeaways (Section 1.5)

- **Layering** breaks a complex system into manageable pieces — each layer offers a service to the layer above, using services from the layer below.
- Layering's main benefit: **modularity** (you can change a layer's implementation without breaking the rest of the system, as long as its service to others stays the same).
- The **Internet protocol stack has 5 layers**: Application → Transport → Network → Link → Physical.
- Data unit names by layer: **Message** (App) → **Segment** (Transport) → **Datagram** (Network) → **Frame** (Link).
- **TCP** = reliable/connection-oriented; **UDP** = unreliable/connectionless.
- **IP** is the one universal network-layer protocol — often the network layer is just called "the IP layer."
- **Encapsulation** = wrapping data with a header at each layer going down; **de-encapsulation** = stripping headers going back up at the receiver.
- **Hosts** implement all 5 layers; **routers** implement layers 1–3; **link-layer switches** implement only layers 1–2.
