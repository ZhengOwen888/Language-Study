# 1.4 Delay, Loss, and Throughput in Packet-Switched Networks

> **Big Idea:** Networks can't move infinite data instantly with zero loss - that's physically impossible. This section quantifies the three real limitations: **delay** (how long things take), **loss** (packets that don't make it), and **throughput** (how much data per second actually gets through).

---

## 1.4.1 Types of Nodal Delay

> **Nodal delay** = the total delay a packet experiences at ONE node (a router or host) before continuing on its journey.

There are **4 components** of nodal delay:

| Delay Type | Symbol | What it is | What it depend on | Typical size |
|---|---|---|---|---|
| **Processing Delay** | `d_proc` | Time to examine the packet's header (decide which outbound link) + check for bit errors | Router's processing speed | Microseconds or less |
| **Queuing Delay** | `d_queue` | Time the packet waits in the buffer/queue before it can be transmitted | How much congestion/traffic is ahead of it in line | Microseconds to milliseconds - **varies a lot**, packet to packet. |
| **Transmission Delay** | `d_trans` | Time to PUSH all of the packet's bits onto the link | Packet size (L) and link rate (R) -> `L/R`| Microseconds to milliseconds |
| **Propagation Delay** | `d_prop` | Time for a bit to physically travel across the link, once pushed on. | Distance between nodes (d) and propagation speed (s) -> `d/s` | Milliseconds (can be much more for satelite links) |

### Total Nodal Delay Formula
$$d_{nodal} = d_{proc} + d_{queue} + d_{trans} + d_{prop}$$

> **Note:** `d_proc` and `d_prop` are usually small/negligible in modern high-speed networks; `d_queue` is the most variable/important one to study: `d_trans` matters a lot on slow links.

### Transmission Delay vs. Propagation Delay - The #1 Point of Confusion

| | Transmission Delay | Propagation Delay |
|---|---|---|
| **What it measures** | Time to PUSH the packet's bits onto the link | Time dor a bit to physically TRAVEL across the link |
| **Formula** | `L/R` (L = packet size in bits, R = link rate in bps) | `d/s` (d = distance, s = propagation speed of the medium) |
| **Depends on ...** | Packet size and link speed | Distance between nodes and the medium |
| **Does NOT depend on...** | Distance at all | Packet size or link speed at all |

**Caravan Analogy (memorize this one - shows up on exams a lot):** Picture a 10-car caravan (= a packet, where each car = 1 bit) approaching a tollbooth (= a router) on a highway (= a link). The tollbooth must let ALL 10 cars through, one at a time, befire the caravan can continue - the TIME TO DO THIS is the **transmission delay** (how long it takes to "push" the whole caravan onto the highway). Once a car leaves the tollbooth, the TIME IT TAKES TO DRIVE to the next tollbooth is the **propagation delay** (has nothing to do with how many cars are in the caravan - just distance and speed).

## 1.4.2 Queueing Delay and Packet Loss

### Traffic Intensity - The key formula for queuing delay

$$\text{Traffic Intensity} = \frac{La}{R}$$

**Purpose:** This ratio tells you wether a queue is going to be a problem - specifically, wether packets are arriving FASTER than they can be sent out.

| Variable | Meaning | How to find it |
|---|---|---|
| **L** | Size of each packet, in bits/packet (assumes all packets are the same size) | Given directly |
| **a** | Average **arrival rate** of packets at the queue, in packets/sec | Given directly |
| **R** | Transmission rate of the outbound link, in bits/sec | Given directly |
| `La` | The average rate at which BITS (not packets) arrive at the queue | Just L * a |

> **The Golden Rule of traffic engineering:** Design your system so **La/R < 1 **.
> - If **La/R > 1** -> bits are arriving faster than they can leave -> the queue grows **without bound** -> infinite delay (in theory). This is the network equivalent of "more people are entering a room than leaving it - the room will eventually overflow."
> - If **La/R** is close to 0 -> queue is almost always empty -> delay ≈ 0.
> - If **La/R** is close to 1 (but under) -> delay grows **rapidly**, even from small increases in traffic.
> like rush hour traffic where a tiny more congestion causes a huge jump in delay.

### Packet Loss
- Real queues have a **finite** (limited) size - they can't hold infinite packets.
- When a packet arrives and the queue is **already full**, the router simply **drops it** -> **packet loss**.
- From the sender's perspective, a lost packet just... never arrives at the destination.
- Higher traffic intensity -> higher probability of packet loss.
- Lost packets are sometimes **retransmitted** end-to-end to makke sure data eventually gets through (covered in later chapters).

## 1.4.3 End-to-End Delay

### Formula (generalizes the packet-switching formula from Section 1.3!)

$$d_{end\text{-}to\text{-}end} = N(d_{proc} + d_{trans} + d_{prop})$$

*(This assumes an uncongested network - i.e., queuing delay is negligible - and that every node has the SAME `d_proc`, `d_trans` (=L/R), and `d_prop`.)*

| Variable | Meaning |
|---|---|
| **N** | Number of links (= N-1 routers) between source and destination |
| `d_proc`, `d_trans`, `d_prop` | Same delay definitions as above - assumed identical at every node here |

> **Compare to Section 1.3's formula:** `d = NL/R` only accounted for transmission delay. This new formula ADDS processing delay and propagation delay into the same idea - it's the same concept, just more complete.

### Traceroute

> **Traceroute** = a real diagnostic tool that reveals the actual routers (path) a packet takes to reach a destination, AND measure the round-trip delay to each one.

**How it works:**
- If there are N-1 routers between source and destination, the source sends **N special packets** (one addressed with marker for each router along the path, e.g., packet "n" is meant to make the nth router respond).
- Each router that recieves its numbered packet sends a short reply back to the source instead of forwarding it - revealing that router's name/address and the round-trip time.
- The whole thing is repeated **3 times** per router, so you get 3 router-trip time measurements per hop.
- Since queuing delay varies over time, it's normal to see delay #12 to be SHORTER than delay #11 in real traceroute output - later routers aren't always slower.
- A sudden BIG jump in delay between two consecutive hops often indeicates a long-distance link (e.g., a transalantic fiber cable) causing a large propagation delay.

### Other End-System Delays
- **Media Packetization Delay** (important for VoIP/voice calls): the time needed to fill up a packet with digitized voice/audio before it can even be sent. This adds to perceived call latency.

## 1.4.4 Throughput

> **Throughput** = the actual rate (bits/sec) at which is successfully being transferred between two end systems.

| Term | Definition |
|---|---|
| **Intantaneous throughput** | The rate at RIGHT NOW, at a specific moment (what a download progress bar shows) |
| **Average throughput** | `F/T` - total FILE size (F, in bits) divided by Total Time (T, in seconds) to transfer it |

### The Bottleneck Rule - THE most important throughput concept

> **For a path with multiple links, the throughput is limited to the SLOWEST link along the path** - this is called the **bottleneck link**.

$$\text{Throughput} = \min\{r_1, R_2, ..., R_N\}$$

**Analogy:** Think of data like water flowing through a series of connected pipes of different widths.
- no matter how wide most of the pipes are, the water can only flow as fast as the **narrowest** pipe allows.

**Worked example:** Downloading a 32 million-bit MP3 file where the server sends at `Rs = 2 Mbps` and your access link is `Rc = 1 Mbps`:
- Bottleneck = min(1 Mbps, 1 Mbps) = **1 Mbps**
- Transfer time = `32,000,000 bits / 1,000,000 bps` = **32 seconds**

### Important naunce: Throughput depends on SHARED traffic too, not just link speeds!

- If you're the ONLY traffic on the network -> throughput = min tranmission rate along your path (simple bottleneck rule above).
- If OTHER traffic is sharing a link with you -> that shared link may give you only a FRACTION of its rate, even if its total rate is high.

**Example:** 10 users share one core link of rate R = 5 Mbps (each server access link Rs = 2 Mbps, each client access link Rc = 1 Mbps). If the shared link divides its 5 Mbps evenly among all 10 downloads -> each download only gets `5 Mbps / 10 = 500 kbps` - even though each user's own access links (2 Mbps and 1 Mbps) could individually handle more. The SHARED core link becomes the real bottleneck here, not the access links.

> **REAL-world takeaway:** In today's Internet, the core is usually over-provisioned (very fast, rarely congested) - so the **access network** (the "last mule" to your home/device) is typically the actual bottleneck for most users.

## Quick Review — Key Takeaways (Section 1.4)

- **4 types of nodal delay:** processing, queuing, transmission, propagation → `d_nodal = d_proc + d_queue + d_trans + d_prop`.
- **Transmission delay** (`L/R`) = pushing bits onto the link (depends on packet size & link rate, NOT distance). **Propagation delay** (`d/s`) = bits traveling across the link (depends on distance & medium, NOT packet size).
- **Traffic intensity** = `La/R` — must be ≤ 1, or queuing delay grows unbounded. As it approaches 1, delay increases sharply.
- **Packet loss** happens when a full queue can't accept an arriving packet.
- **End-to-end delay** = `N(d_proc + d_trans + d_prop)` (uncongested network assumption).
- **Traceroute** reveals the path + round-trip delay to each router along the way.
- **Throughput** = the actual data transfer rate; **bottleneck link** = the slowest link on the path, and it determines the max possible throughput: `min{R1, R2, ..., RN}`.
- Shared/contended links can reduce your throughput below what your own access link could otherwise support.
