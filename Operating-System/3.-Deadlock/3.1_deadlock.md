## 3.1.0 Objectives

- Understand what a resource is.
- Understand what a deadlock is and what are its requirements.
- Understand what algorithms are used to detect deadlocks.
- Understand how avoiding deadlocks is practically impossible.
- Understand how we can prevent deadlocks.


## 3.1.1 Resources

Resources are objects that can be granted and used by the processes that requested them.

| Resource Type | Description |
|---|---|
| Preemptable | Resource that can be taken away from the process owning it with no side effects. |
| Nonpreemptable | Resource that can not be taken away without causing potential failure. |

### Sequence to use a Resource
1. Request the resource.
2. Use the resource.
3. Release the resource.


## 3.1.2 What is Deadlock?
Deadlock happens when a set of processes is waiting for another event to happen, but that event can only be triggered by another process in the same set. In simple words, every processes are stuck in a cycle of waiting for resource. This specific deadlock where resources are involved are called resource deadlocks.

### Conditions for Resource Deadlock
1. Mutual exclusion, Condition where resources can not be shared simultaneously between processes.
2. Hold-and-Wait, Condition where a process is hogging one resource while waiting for another.
3. No-Preemption, Condition where you can't focibly take away a resource from a process.
4. Circular-Wait, Condition where each process in a set is waiting for the other process in a cycle to release their resource. (e.g. Process A  waits on B, B waits on C, C waits on A -> a cycle with no exit)

## 3.1.3 Deadlock Detection and Recovery

### Deadlock Detection with One Resource of Each Type

We can use a graph to represent the resources and processes in a system. Essentially we will perform a depth first search (DFS) traverse each edge once and see if we land back to a visited node.

| Element | Shape | Edge Direction |
|---|---|---|
| Resource | Square | Points **to** a process (acquired) |
| Process | Circle | Points **to** a resource (requesting) |

### Graph Cycle Detection Algorithm (One Resource of Each Type)

**Setup (Run once for every node):**
- Pick a node N as the starting node.
- Initialize an empty list **L**.
- Mark all edges as **unvisited**.

**Steps:**

1. Add the current node to the end of **L**.
   - If the node appears in **L more than once** -> a cycle exists, **terminate**.

2. Check if the current node has any unvisited outgoing edges.
   - **Yes** -> go to step 3.
   - **No** -> go to step 4.

3. Pick an unvisited outgoing edge at random, mark it as visited, follow it to the next node, and **go back to step 1**.

4. If the current node is the **start node** -> no cycle exists, **terminate**.
   Otherwise -> dead end reached. Remove the current node from **L**, backtrack to the previous node, and **go back to step 2**.


### Deadlock Detection with Multiple Resources of Each Type

When there are multiple resources of each type of a resource. We can use matrices and vectors to keep track of the details related to each resource

| Vectors | Description |
|---|---|
| Existing (E) | Represents the total number of resource of each type. Has one row and the number of columns equals the number of unique resources.|
| Available (A)| Represents the number of resources that are still left. Has one row and the number of columns equals the number of unique resources.|
---
| Matrices | Description |
|---|---|
| Current Allocation Matric (C)| Each row represents the number of resources each process is holding. Each column represents the number of a specific resource that process is holding. |
| Request Matrix (R)           | The request matrix has the same number of rows and columns as the (C) matrix. The only difference is that it tells us what resources each process is still requesting. |
---

> [!NOTE]
> Therefore, **Sum of all row vectors in (C) + (A) = (E)**. The total number of existing resources will be equal to the sum of the total resources the processes hold and the available or remaining resources.

### Matrix Cycle Detection Algorithm (Multiple Resource of Each Type)

**Setup:**
- Have a horizontal vector (E) representing the total number of resources.
- Have a horizontal vector (A) representing the remaing number of resources.
- Have a Matrix (C) where each row represents a different process and each column represent the number of resource of a specific type that process holds.
- Have a Matrix (A) where it is the same as Matrix (C), except instead hold information on what resources the process is still requesting.
- Mark all processes as **Not Done**.

**Steps:**
1. Look for a Process that is **Not Dont** on the ith row, where their ith row on the (R) matrix is less than (A). Basically, look for a process that is requesting less than the availble resources.

2. If such Process is found, add the ith row of C to A, and mark the Process as **Done** and go back to step 1. Basically, add return the resources that the process is holding by adding the amount the process currently hold to the available resources.

3. If no such Process, the algorithm Terminates.

> [!NOTE]
> Any process that is still marked as **Not Done** when the algorithm terminates are considered deadlocked.

### Deadlock Recovery

With the algorithms to detect deadlocks, we now need ways to recover from one.

1. **Recovery Through Preemption** - When a deadlock is detected, we will manually and forcibly take away resources from a process.

2. **Recovery Through Rollback** - Periodically create snapshot of processes called **checkpoints**. These checkpoints contain the entire state of a process at the time meaning it will also keep track of the resources that the process hold at that exact time. When a deadlock detected, we will perform a rollback for the process that hold the resource that another needs. All the work that is done by the rolled back process is lost. Basically the process will be reset to a moment when it did not have the resource.

3. **Recovery Through Killing Processes** - When a deadlock is detected, we will kill a process that holds the resource that is needed. However, it is best to kill a process that can be rerun from the beginning with no side effects.

## 3.1.4 Deadlock Avoidance

| States of the Processes | Description |
|---|---|
| Safe | There exist a scheduling order in which every process can run until completion, even if all of them request their **max number** of resouces immediatly. |
| Unsafe | There exist no such scheduling. Note that an unsafe state does not mean that it leads to deadlock, it just means that there is no gaurantee that all process will complete.|

We can use the banker's algorithm to see if granting a resource to a specific process will lead to a safe or unsafe state.

> [!NOTE]
> The Banker's Algorithm is an extension to the previous deadlock detection algorithm (Matrix Version).

### Banker's Algorithm (Single Type Resource)

**Setup:**
- Keep a table that looks something like this.
---
| | has | max |
|---|---|---|
| Process A | | |
| Process B | | |
- **has** represents the number of resources the process is currently holding.
- **max** represents the max number of resources the process will hold before. completion.
- use a seperate variable **free** to keep track of the current available resources.
- Mark all Processes as **Not Done**

**Steps:**
1. Pick a process on the ith row that is **Not Done**, where max - has < free.
2. If such process is found free all its resource by doing free = free + has and mark the process as **Done**.
3. If no such process is found, the program is terminated.

> [!NOTE]
> If there are still processes that are marked as **Not Done**, then the original state of the processes are unsafe.

### Banker's Algorithm (Multiple Type Resources)

A more general banker's algorithm can handle multiple types of resources and is very similar to the previous deadlock detection algorithm (Matrix Version for Multiple resource types). The only difference being that we have to set up an extra vector (P).

| Vector | Description |
|---|---|
| P | Represents the total number of resources that are being held by the processes. Has one row and the number of columns equals the number of unique resources. |

**Setup and Steps**: [Matrix Cycle Detection Algorithm (Multiple Resource of Each Type)](#matrix-cycle-detection-algorithm-multiple-resource-of-each-type)

### Problem with the Banker's Algorithm and Deadlock Avoidance
Even though the banker's algorithm can technically predict deadlocks since it takes advantage of the fact that it was provided the number of resources each process will ever need. However, in a real world scenario, we are not able to predict or know how much resource each process will need until it completes. So in the end, deadlock is essentially **impossible**.

## 3.1.5 Deadlock Prevention

If we can prevent one of the conditions listed as requirements for a deadlock, we can possibly reduce the frequency of deadlocks.

### Preventing Mutual Exclusion Condition
To eliminate mutual exclusion condition we can allow resources like read only data to be shared between processes freely. However, some resourced physically can not be shrared between processes, for example a printer.

So Instead of letting the processes directly fight over the printer, we introduce a middlemain that:
- Collects all the output from every process into a spool (buffer on disk)
- Is the only process that will ever touch the real printer.

However this can create a new problem if the middleman waits for the complete output before printing (which is the safe choice) a new deadlock will emerge. If two processes each fill up half the spool (buffer on disk), both will be waiting for more space to finish writing the output, but none will finish, so none will ever free up the space.

### Preventing Hold-and-Wait Condition
To elimite the hold-and-wait condition, you want to make sure that a process never holds one resource while waiting for another.

**Approach 1**: We can aquire every resource at once at the start of the program and release every resource acquired at the very end of the program.

**Problems with approach 1**:
- Processes often do not know what they will need in advance so aquiring all resources at once at the start can be wasting.

**Approach 2:** We can release all resources currently held before acquiring the next resource.

**Problems with approach 2**:
- Processes will lose progress that was already made with the held resource and will have to start over. For example, if the process was modifying a file and was then taken and modifed by another process, This current process will have to start over when it gets the file back.


### Preventing No-Preemption Condition
To eliminate the no-preemption condition, we allow the operating system (OS) to forcibly take away the resources from a process when needed, but this is only possible for some resources.

**Problems with this method**:
- If you forcibly take a resource away from a process midway its execution, the output might be ruined or invalidated.

### Preventing Circular-Wait Condition
To eliminate the circular-wait condition, we need to make it impossible for a cycle to form.

**Approach 1**: One resource at a time for each process. This makes it so that the process can never hogg (holding while wanting more) a single resource when it is still requesting for more. This completely eliminates circular wait.

**Problems with approach 1:**
- This is similar to the earlier problem we saw earlier. If a process release a resouce when it is not done with it then the progress it made with that specific resource will be invalidated and will have to start over when it reacquires that resource.

**Approach 2**: Numerical ordering for each Resource and add a simple rule on top of it. For example, we number each of the 3 resouces in order from 1 to 3. The rule is to only allow a process request a resource with a higher number that the one it currently holds. Another variation, instead of higher it would be lower.

**Problems with approach 2:**
- The problem with this approach is that it is very hard to find numbering that works for everyone, and different processes can require resources in different orders.
