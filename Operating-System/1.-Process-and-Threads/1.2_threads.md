## 1.2.0 Objectives
- Understand what a thread is and its different models.
- Understand what certain pitfalls occurs with threads.
- Understand what the per process and per thread properties.
- Understand how threads are implemented in the user space and kernel space.
- Understand how we can use both user and kernel threads to improve efficiency.

## 1.2.1 What is a Thread
A thread is created by a process that allows the sharing of a single address space.
It is more light weight than processes and are easier and faster to create and destroy.

## 1.2.2 Thread Models

Single threaded Process
- No Parallelism and involves blocking system calls.

Multi Threaded Process
- Allows Parallelism and still involves blocking system calls.
- One thread fetches requests and hands it to other threads, these threads will then hand this request to the hardware. The original thread will block and wait until it gets the result or resource from the hardware.

Finite State Machine:
- Allows Parallelism, but with non blocking system calls.
- One thread hands the work to the hardware and moves to the next task until an interrupt signal comes to notify the thread that the result or resource is ready from the hardware for the previous task.

## 1.2.3 Thread Caution
- There is no protection between threads, It is impossible and it should not be necessary. Every - Every thread can access every memory address within the process' address space since it is shared.
- If you use fork() and pthread_create() together: make sure to fork() then pthread_create() and nother the other way around. This is to acoid the "Ghost Mutex" problem.
- Ghost Mutex Problem - This occurs when a thread acquires a mutex lock and terminates unexpectedly without unlocking it which leaves the mutex in a deadlocked states. In this case, when fork() copies a locked mutex into a process, but doesn't copy the owner thread needed to unlock it, leaving the child permanently deadlocked.

## 1.2.5 Thread Implementation in User Space
- Each process needs it own private thread table to keep of per thread properties.
- User level threads allow each process to have its own customized scheduling algorithm.
- In user level threads, the OS pauses the entire process. This will freeze all the other threads in the system which defeats the purpose of multitasking.
- In user level threads, if a single thread never ends, other threads will not get to run. this OS does not know anything about the threads in the process because they are implemented in the user space. The only thing the OS can do is start and stop a process which would also freeze all threads.

## 1.2.6 Thread Implementation in Kernel Space
- The kernel will have a single thread table to keep thrack of all threads in the system.
- Kernel level threads does not allow the user to customize the scheduling algorithm, it is done by the operating system.
- kernel level threads are more expensive to create and destroy, so old threads are recycled. The old threads are marked as not runnable and used afain when a new thread is needed.

## 1.2.7 Thread Implementation (Hybrid)
**Many to One**
- Large pool of threads in the user space is mapped to a single thread in the kernel space.
- If a single thread in the kernel space is blocked, then all the user threads mapped to it are also blocked.

**Many to Many**
- Large pool of threads in the user space is mapped to many threads in the kernel space.
- If one thread in the kernel goes to sleep or blocks, then there are still other kernel thraeds that are awake to take care of the user threads.
