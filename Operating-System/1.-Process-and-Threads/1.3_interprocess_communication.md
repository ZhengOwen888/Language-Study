## 1.3.1 What is Interprocess Communication
Interprocess communication are techniques processes uses to communicate with each other. When processes or threads communicate with each other there is something called race confitions. Race conditionis when two or more processes are reading or writing some shared data and the final result depends on who runs precisely when.

## 1.3.2 Mutual Exclusion

**Critical Region**
- The part of the program where the shared memory is accessed.

**Rules to Follow for Mutual Exclusion**
1. No two processes may be simultaneously inside their critical regions.
2. No assumptions may be made about the speed or the number of CPUs.
3. No process running outside its critical region may block any process.
4. No process should have to wait forever to enter its critical region.

## 1.3.3 Ideas to Achieve Mutual Exclusion

### Disabling Interrupts
We can disable interrupts from clocks so that tasks are finished before another starts. (Violates 2, 3, 4)

### Lock Variables
We can use a lock variable, 0 means no process is in the critical region and 1 means that there is a process in the critical region. This however also causes race conditions for the same lock variable. (Violates 1, 4)

### Spin Locks
We can use a special type of lock called the **spin lock**. This uses busy waiting where a process waits for the lock to become a certain value say 1 or 0. This however, wastes CPU time because it could have been doing other tasks instead of waiting. Additionally, one process might be slower than the other and would block the other processes from continuing because the lock value has not been updated yet. (Violate 2, 3, 4)

### Peterson's Solution
We can use a solution made by Peterson. This is used for two entities. It ensures that two processes don't collide by having each process declare its interest and then defer the turn to the other, entering only if the other process is uninterested or has deffered the turn back to them. Turn in this context means "whose turn it is to wait" and not "whose turn it is to go". (Violate 2)

### TSL (Test and Set Lock) Instruction
We can use a atomic instruction called TSL in assembly that is guaranteed to be indivisible for reading a word and storing it. It locks the memory bus to prohibit other CPUs from accessing memory until it is done.

The way TSL instruction works is that it grabs the lock value and stores it in a private register and simultaneously replaces the value of the lock to 1 right after. Then it compares, if the previous value of lock was 0, then the process knows that it caught the lock when it was opened and will proceed to the critical section. Otherwise if it is a 1 then the Lock was alrady taken and the process will loop and repeat. (Violate 2, 3, 4)

### XCHG (Exchange) Instruction
We can use another atomic instruction called XCHG in assembly. This method works by attempting to swap a 1 in your hand for whatever the lock value was. If you pull a 0, then you successfully acquired the lock and left it locked for other processes. If you recieve a 1 then you must keep trying because it was taken by other processes.

Basically store 1 in a general register, swap that with the value held by the lock. compare the lock value with value 0. If it is equal to 0 then the process can go to the critical region, otherwise keep trying to acquire the lock. (Violate 2, 3, 4)

## 1.3.4 Better Solutions for Mutual Exclusion

### Semaphores
A semaphore is a counter variable that is used as a signaling mechanism.

- Binary Semaphore: (0 or 1) Any processs can signal to wake someone else up.
- Counting Semaphore: (Value = N) Used to manage a pool of resources.
- Operations:
    - down(): If value is greater than 0, decrement and continue. If the value is 0, the process is put to sleep.
    - up(): Increments the value, If there are processes sleeping in this semphore, one of them is woken up to complete its down operation.

### Mutex Locks
Another special type of lock that has the concept of ownership.
- If lock is 1 (acquired by another process), the process is moved to a wait queue and suspended or put to sleep. when the owner releases it, the OS picks a process from the queue to wake up.
- Only the process that locked it can unlock it
- Mutex locks are expensive because it needs to put a thread to sleep and wake them back up. This is why spin locks are used with mutex locks. We can use spin lock from the start for a while and then switch to mutex lock when we wait too long.
