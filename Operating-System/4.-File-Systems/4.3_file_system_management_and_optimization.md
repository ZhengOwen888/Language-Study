## 4.3.2 Block Size
Alright, now that we decided to store files in fixed sized blocks in the disk, how do we manage that space efficiently. We need too figure out the size of blocks we want to use.

| Block Size | Tradeoff |
|---|---|
| Large Blocks | Fast reads (fewer seeks) but waste space (a 1 byte file will still use an entire block).|
| Small Blocks | Space efficient but slow (more blocks means more seeks and rotational delays per file)|

> [!Note]
> Wasting a little space on small files barely matters since the disk is mostly dominated by a few large files.

- Historically **1KB** to **4KB** was the standard compromise.
- The space and data efficiency curve cross near when block size is ```64KB```, but at that size neihter the space or data efficiency is great. (space = ```10%``` disk space utilization, data rate = ```5MB/sec```)

### Calculating the Time to Read a Block

We can calculate the time to read blocks with the following formula:
```
Time (ms) = seek time + rotational delay + transfer time
```
| Variable | Decription |
|---|---|
| Seek Time         | The time for the disk's read/write head to physically move across the disk to the right track where the block lives. |
| Rotational Delay  | Once the head is on the right track, the disk needs to spin until the right sector rotates underneath the head.|
| Transfer Time     | This is the actual time spent reading the data once the head is in position. |

#### Example
Lets say a disk has ```1MB``` per track. The seek time is ```5ms``` and the time for a disk to make one full rotation is ```8.33ms```. Then the time it takes to read a block of ```k``` bytes is:
```
Time(ms) = 5 + ((0 + 8.33) / 2) + (k / 1000000) * 8.33
```
- seek time = ```5ms```
    - It takes ```5ms``` for the head to find the correct track with the block.
- rotational delay = ```((0 + 8.33) / 2)```
    - We need to find the average rotational delay.
    - **Best case** scenario, the sector you need is just about to pass under the head the moment the arm finishes seeking so you wait almost 0ms.
    - **Worst case** scenario, the sector just need just passed under the head a split second before the arm arrived, so you have to wait for the entire disk to complete a full rotaion to being it back around.
    - Since both extremes are equally likely, on **average** you wait for half a rotaion, which is why we do ```((0 + 8.33) / 2)```.
- transfer delay = ```(k / 1000000) * 8.33```
    - The time it takes to read 1 byte would be the time for the full rotaion divided by the number of bytes per track, so ```8.33 / 1000000```. then to find the time to read k bytes we just multiply ```8.33 / 1000000``` by ```k``` which gives us: ```(k / 1000000) * 8.33```.

## 4.3.3 Tracking Free Blocks

Now that we have chosen the block size, we need to be able to keep track of free blocks (blocks that are not being used).

### Linked List of Free Blocks
- Free block addresses will be stored inside the disk blocks themselves.
- Each block holds as many free block numbers as it will fit.
- One entry is reserved for a pointer to the next disk block that stores information on more free blocks.

#### Example
Lets say we have a ```1TB``` disk and each block is ```1KB```. Each disk block is represented by a ```32bit``` disk block number. To store all these addresses we will need a this many blocks:

```
Total Blocks = Disk Size / Block Size = 1TB / 1KB = 1 billion blocks

Entries per block = Block Size / Entry Size = 1KB / 32bit = 1 KB / 4 byte = 256 entries

Entries that Represent Free Blocks per Block = 256 - 1 = 255

Total Blocks to Represent all addresses = 1 billion / 255 = 4 million blocks
```

### Bitmap
- One bit per block on the entire disk.
- ```1``` = free, ```0``` = allocated (or vice versa).
- More compact than linked list.
- Exception: linked list uses less space only when the disk is nearly full (few free blocks = short list)
#### Example
Lets say we again have a ```1TB``` disk and each lock is ```1KB```. Then the number of blocks to store all the free blocks is:

```
Total Block = Disk Size / Block Size = 1 TB / 1KB = 1 billion blocks.

Total Bits to Represent all Block Addresses = Total Blocks = 1 billion bits

Total Blocks to Represent all addresses = (1 billion bits / 8 bits) / 1KB = 130,000 blocks
```

### Comparison
| | Linked List | Bitmap |
|---|---|---|
| Spaced Used               | Proportional to free blocks   | Fixed (always n bits for n blocks)|
| More efficient when ...   | Disk nearly full              | Disk has many free blocks         |
| Simpler to manage?        | No                            | Yes                               |


### Problems with Free List Method
- How it Works Normally:
    - Only **one block** of free pointers is kept in main memory at a time.
    - **File created** -> take blocks from the in-memory block, when **empty**, read next block from disk.
    - **File deleted** -> add freed blocks to in-memory block, when **full**, write to disk.

- The Problem - Unnecessary disk I/O
    - If the in-memory block is almost empty and many temporary files are created and deleted rapidly then:
    - Creating new files empties it again -> must read it back from disk.
    - This cycle repeats constantly -> lots of unnecessary disk I/O

- The Fix - Keeping the in-memory block **Half-Full**
    - Split it - Keep half the pointers in memory, write the other hald to the disk.
    - Result: the in-memory block will stay roughly half-full.
    - Now it can handle both file creation (taking blocks) and deletion (adding blocks) without touching disk too often.

## 4.3.4 File System Backup
Losing a file system is far worse than losing hardware. A computer can be replaced in hours, data lost forever and often cannot be recovered at any cost.

| Reason | What is Covers |
|---|---|
| Recover from Disaster | Disk Crash, fire, flood, hardware failure. |
| Recover from stupidity| Accidently deleted a file you still needed.|

### Five Practical Issues Before Going Technical
#### 1. Don't Back Everything Up
Some things don't need to be backed up:
- Executable/binary files - can be reinstalled from manufacturer's website or DVD
- Temporary file directories - no useful data.
- ```./dev``` in UNIX - contains special I/O device files, backing them up is dangerous since the backup program will hang trying to read them.

#### 2. Use Incremental Dumps
- **Full Dump** - complete backup of everything, done periodically (weekly/monthly)
- **Incremental Dump** - only files changed since the last full dump, done daily
- **Finer Incremental** - only files changed since they were last dumped individually.

> [!Note]
> Trade-off: finer increments = less time to backup, but more complex to restore (must restore full dump first, then each incremental in order).

#### 3. Compression is Risky
- Compressing backup data saves space but introduces fragility.
- A **single bad spot** on the tape can break the decompression algorithm, making an entire file or entire tape unreadable.
- The decision to compress must be weighed carefully.

#### 4. Active Filesystems are Hard to Back Up
- Files are being added, deleted, and modified during the backup -> result may be inconsistent.
- Solution: snapshots - copy critical data structures to freeze the filesystem state at one moment, then require future changes to copy blocks rather than modify them in place.
- The snapshot represents a consistent point-in-time that can be backed up at leisure.

#### 5. Physical Security Matter Too
Technical backup systems are useless if:
- Backup tapes are left unguarded in an office anyone can wolk into.
- Backups are stored on-site and destroyed in the same fire that kills the computers.


### Two Dumping Strategies

### Physical Dump
- Copies every disk block sequentially from block 0 to the last block.
- Extremely ismple and fast (runs at disk speed)
- Skips unused blocks and bad blocks if it has access to the free-block list.

#### Advantages
- Simple, nearly bug free.
- Very fast

#### Disadvantages
- Cannot skip specific directories
- Canoot do incremental dumps
- Cannot restore a single file, you get everything or nothing

#### Bad Block Handling
- If disk controllerhides bad blocks, physical dump works fine.
- If OS knows about bad blocks then dump program must skip them or it will hang on read errors.

### Logical Dump (Most Common)
- Starts at one or more specified directories.
- Recursively dumps all files and directories that have changes since a given base date.
- Also dumps unmodified directories that lie on the path to modified files (so the path can be reconstructed on restore).

#### Advantages
- Can back up specific directories
- Supports incremental dumps
- Can restore a single file or directory on request

### The Four Phase Logical Dump Algorithm

Uses a bitmap indexed by I-node number to track what needs to be dumped.
1. Phase 1
    - Starting from the starting directory, recursively walk the entire file tree and set mark every directory and file witin.

2. Phase 2
    - Walk through the tree again and unmark directories that does not contain any modified files.

3. Phase 3
    - Scan I-nodes in numerical order.
    - Dump every directory stilled marked after phase 2.
    - Each directory is prefixed with its attributes (owner, times, permissions) so they can be restored lat correctly.
> [!Note]
> Directories need to be dumped first because when you restore you need the directory structure to exist before you can put the files in.

4. Phase 4
    - Dump every modified file still marked.
    - Each file is also prefixed with its attributes

### Why Dump Unmodified Directories
- Unmodified Directories just means the directory's own attributes haven't changed, things like name, owner, permissions, and timestamps. It says nothing about what's inside. So, a directory can be "unmodified" and still contain modfied files deep within it.
- Essentially Directories need to be dumped so that there is a container that exists to place the modified files within.

### Restoring From Logical Dumps
1. Create an empty filesystem on target disk.
2. Restore the most recent **full dump** - directories appear first creating the skeloton or containers.
3. Then restore each **incremental dump** in chronological order.

### Important And Tricky Edge Cases

#### Free block List
- The free bloock list is not a file -> so it is **not dumped**
- Must be **rebuilt from scratch** after restore
- This is always possible: free blocks = all blocks not contained in any restored file.

#### Hard Links
- A file linked to multiple directories must be **restored only once**
- All directories that pointed to it must point to the same restored copy

#### Sparse files (Files with Holes)
- UNIX allows files with gaps - data written at offset 0, then again at offset 500 MB, with nothing in between.
- The "nothing in between" is a **hole** - it takes no disk space.
- If not handled properly, restoring the file fills the hole with xeros -> file becomes enormous (potentially gigabytes)
- Holes must be detected and preserved during restore.

#### Special Files
- Device files, named pipes, and similar special files must **never be dumped**, regardless of which directory they appear in.
- They are not real files and cannot be meaningfully backed up or restored.


## 4.3.5 File System Consistency
The OS reads blocks, modifies them in memory, then write them back. If the system crashes between those writes, some blocks get updated and some don't leaving the filesystem in a half-finished and inconsistent state.

### The Solution - Filesystem Checker Program
Run a utility that examines the filesystem and repairs inconsistencies by exploiting the filesystem's **inherent redundancy**, the same information is recorded in multiple places (I-nodes, directories, free lists), so they can be cross checked against each other.

| OS | Checker Program |
|---|---|
| UNIX    | ```fsck``` |
| Windows | ```sfc```  |

These are run at boot time, especially after a crash. Each checker verifies each disk parition independently.

### Two Seperate Checks

#### Check 1 - Block Consistency
Builds two counter tables, one entry per block, both initialised to 0.
| Table | What it Tracks |
|---|---|
| Table 1 | How many times each block appears in a file (via inodes) |
| Table 2 | How many times each block appears in the free list |

The checker program will read all I-nodes and builds the list of blocks each **file** uses -> increments Table 1. Then reads the **free list** -> increments Table 2.

> [!Note]
> In a **consistent filesystem**, every block has exactly a 1 in one table and a 0 in the other. It is either in use or it's free, never both, never neither.

#### Four Possible States After A Crash
| Table 1 (in file) | Table 2 (in free list) | Situation | Severity | Fix |
|---|---|---|---|---|
| 1 | 0 | **Normal** - Block is in use              | None  | Nothing |
| 0 | 0 | **Missing Block** - belongs to neither    | Low   | Add to free list |
| 0 | 2 | **Duplicate** in free list                | Low   | Rebuild the free list |
| 2 | 0 | **Duplicate** data block - two files claim the same blockk | Critical | Copy block, give one copy to each file and report the error |
| 1 | 1 | **In Use** and **Free** | Critical | Remove the block from the free list |

#### Why Duplicate Data Blocks are Critical
If two files share the same block and one file is deleted:
- That bolck goes onto the free list.
- The other file still points to it.
- The block gets reassgiend to a new file.
- The other file's data is now silently corrupted.

> [!Note]
> Duplicate entries in the free list can only occur if the free list is a linked list. With a bitmap it is impossible, since a bit is either 0 or 1, it cannot be 2.


#### Why Being In Use and Free Simultaneously is Dangerous
If a block is both **in use** and **free**:
- The next time any file is created, that block could get allocated to it.
- This will instantly corrupt the file that was already using that block.

#### Check 2 - Directory Consistency
The Checker program walks the entire directory tree from root, building a counter table per file (indexed by I-node number) tracking how many directory entries point to each I-node. It then compares with the number of links recorded in the I-node.

#### Two Things Can Go Wrong
| Situation | Consequences | Severity | Fix |
|---|---|---|---|
| I-node contained link count **too high** | I-node never freed even when all directory entries removed - space wasted | Low | Set link rount to correct value |
| I-node contained link count **too low**  | Count hits zero permaturely when a directory entry is removed -> filesystem marks I-node free and releases its blocks -> another directory now points to reassigned blocks | Critical | Set link count to correct value |

> [!Note]
> Symbolic links do not count toward the link counter - only hard links increment it.


### Why Caused These Duplicates and Mismatches
- **Duplicates appearing in the checker's table** -> caused by hard links, completely normal.
- **Mismatch between checker's count and I-node's count** -> caused by a crash corrupting the I-node's link count mid-write.
- The whole purpose of the checker is to recount from scratch by walking the directories and use that as a fact to fix whatever the I-node is telling us otherwise.

## 4.3.6 File System Performance

Disk access is roughly a million times slower than memory access. We someway to make disk access faster.

### Three Optimization Techniques
| Technique | Core Idea |
|---|---|
| Caching    | Keep recently used blocks in memory to avoid re-reading from disk |
| Read-ahead | Fetch the next block before it's requested |
| Reducing disk-arm motion | Keep related blocks physically close together on disk |

### Technique 1 - Caching
A **cache** is a collection of disk blocks kept in memory for performace. Every read request checks the cache first:
```
Block in cache?     -> serve from memory (no disk access)
Block not in cache? -> read from disk into cache, then serve
```

Blocks are found in the cache using a **hash table** on the device + disk address. The collisions are handled with a linked list off each hash slot.

#### Replacement Policy - Modified LRU
When the cache is full and a new block must be loaded, an old one must be evicted. LRU seems obvious but has a critical flaw:
- If a midified I-node block sits at the back of the LRU list for a long time before being written to disk, a crash in that vulnerable window or frame in time will leave the filesystem.
So a **modified LRU is used instead, asking two question per block:

1. Will this block be needed again soon?
- Blocks unlikely to be needed again (e.g. full data blocks just written) -> placed at the **front** of the LRU list -> evicted quicker.
- Blocks likely to be needed again (e.g. partially full blocks being written) -> placed at the **rear** of the LRU list -> evicted later.

2. Is this block critical to filesystem consistency?
- Critical blocks (I-nodes, directory blocks, indirect blocks) -> written to disk **immediately** when modified, regardless of LRU position.
- Data blocks -> can wait longer befire being written out

> [!Note]
> The reasoning behind this is because, if the user loses a file in a crash, they will be unhapy. If the entire filesystem is corrupted, they will be far more unhappy.

#### So Putting it Together
```
Regular LRU:  one dimension - recency only
Modified LRU: two dimension - recency AND consistency critically
```
| Data Type | Where on LRU List? | When To Write to Disk?|
|---|---|---|
| I-node block | **front** or **rear** | **IMMEDIATELY** (Critical)|
| Data block | **front** (if done with)<br> or<br> **rear** (if still writing)| When **evicted** (Not Critical)|

#### Write Back Strategy - Two Approaches
| Strategy | How it Works? | Pro | Con |
|---|---|---|---|
| UNIX (delayed write) | Keep modified blocks in cache, flush to disk every 30 seconds via ```sync``` call | Efficient - many writes batched into one | Up to 30 seconds of work lost in a crash, removing dish without sync corrupts filesystem |
| Write-through cache  | Write every modified block to disk immediately | Safe - no data lost if disk removed | Much more disk I/O - e.g writing a file one character at a time causes one disk write per character |

### Technique 2 - Read Ahead
When the filesystem serves block ```k```, it secretly schedules a read for block ```k + 1``` befire it;s requested, so it arrives in cache by the time it's needed.

Only works for **sequential access** - However, for **random access** it:
- Wastes dosk bandwidth reading useless blocks
- Pollutes the cache, evicting blockks that might actually be needed
- May cause extra disk writes if those useless blocks are dirty

#### Tracking Access Mode
| Access Mode | Bit | Description |
|---|---|---|
| Sequential Access Mode | 1 | read-ahead enabled|
| Random Access Mode     | 0 | read-ahead disabled|

- File starts in sequential mode (benefit of the doubt)
- A seel clears the bit -> switches to random mode
- Sequential reads after a seek set the bit again

### Technique 3 - Reducing Disk Arm Motion
Seeks are expensive, so keeping related blocks physically close together is a good idea.

#### Block Clustering
Instead of allocating one block at a time, allocate in groups of consecutive blocks.
- e.g. Always allocate 2 blocks at a time (even if only 1 needed right now)
- Sequential reads halve the number of seeks
- Cache still works normally like nothing changed.

> [!Note]
> **Bitmaps** in memory -> easy to find the nearest free block to the previous one. However with **free list** -> much harder because you can't easily tell what's nearby making clustering harder to achieve.

#### I-node Placement
Reading even a short file requires **two disk access**: one fore the I-node and one fore the **data block**. If I-nodes are all at the start of the disk:
```
I-node (start of disk) <-------- long seek --------> Data block (middle / end)
```

| Better Approach | Improvement |
|---|---|
| Place I-nodes in the middle of the disk | Havles the average seek distance between I-node and data|
| Divide disk into **sylinder groups**    | Each group has its own I-nodes, blocks, and free list - I-node and its data are physically nearby |

```
Cylinder group 1            Cylinder group 2            Cylinder group 3
[ I-nodes | blocks ]        [ I-nodes | blocks ]        [ I-nodes | blocks ]
```

When creating a file, the OS tries to allocate data block in the **cylinder group** as the I-node. If none availbale, uses a nearby cylinder group.

### When All of This Becomes Irrelevant - SSDs
All three techniques above exists because of mechanical disk limitations, seek time and rotation delays. However SSDs have no moving parts:
- No seek time - no arm to move
- No rotaional delay - no spinning platter
- Random Access = sequential access speed

> [!Note]
> SSDs introduce a new problem: each block can only be written a limited number of times. The OS must spread writes evenly across the drive (wear leveling) to prevent any single block from wearing out prematurely (too soon).

## 4.3.7 Defragmenting Disks

### How Fragmentaion Builds Up
When an OS is freshly installed, everything is laid out neatly and consecutively:
```
[ OS files | program | free space (one large contiguous block) ]
```

Over time, files are created and deleted, leaving holes scattered everywhere:
```
[ file A | hole | file B | hole | file C | hole | file D | hole | ... ]
```

New files get their blocks spread across these holes, this means that many seeks are used to read a single file, giving poor performance.

### The Solution - Defragmentation
Physically move files around on disk so that:
- Each file's blocks are **consecutive** again
- All free space is **consolidated** into one or more large contiguous regions

### How Defragmentation Works
**Defragmentation** needs a large contiguous free region to use as a staging area, ideally at the end of the partition.

1. Take a fragmented file near the start of the disk
2. Copy all its blocks into the free space at the end
3. This frees up a contiguous gap where the filie used live
4. Place files neatly and consecutively into that gap
5. Repeat across the whole disk

### Files That Cannot Be Moved
| File | Reason |
|---|---|
| Paging file     | Too complex to relocate |
| Hibernation file| Fixed location required |
| Journaling Log  | Active use during defragmentation makes relocation impractical |

These are often fixed-sized contiguous areas, so they don't need defragmentating themselves. Unless one of these immovable files sits near the end of a partition the user wants to shrink, the only solution is:
1. Delete the immovable file
2. Resize the partition
3. Recreate the file

### When Defragmentation Doesn't Help
1. Linux
- Smarter block allocation means less fragmentation

2. SSDs
- **No moving parts** -> no seek time -> fragmentation has no performance impact
- Drfragmentating an SSDs is **actively harmful**:
    - Each block on SSD can only be written a limited number of times so it wears out faster.
