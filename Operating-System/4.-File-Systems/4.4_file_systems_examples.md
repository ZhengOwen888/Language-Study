## 4.4.2 The UNIX V7 File System

### Directory Entry Structure

```
[ I-node number (2 bytes) | file name (14 bytes) ]
```

| Field | Size | Purpose |
|---|---|---|
| I-node number | 2 bytes  | Points to the I-node holding all file information |
| File name     | 14 bytes | Any ASCII character except / (path seperator) and ```NUL``` (used for padding)|
- The 2-byte I-node number limites files per filesystem to 64K
- All actual file information lives in the I-node, not the directory entry

### What the I-Node Stores
Each I-node contains:
- File size
- Three timestamps - creation, last access, last modification
- Owner and group
- Protection/permissions
- Link count - number of directory entries currently pointing to this I-node

#### Link Count Behaviour
- New **Hard Link** created -> count incremented
- Link **Removed** -> count decremented
- Count reaches **0** -> I-node reclaimed, disk block returned to free list.

### Handling Files of Different Sizes - The Indirect Block System
The I-node has a fixed number of slots for block addresses. The Challenge is upporting both tiny and enourmous files. The solution is the indirect block system:
```
Inode
├── Direct address 1  ──→ data block
├── Direct address 2  ──→ data block
├── Direct address 3  ──→ data block
│   ... (10 direct addresses total)
│
├── Single indirect   ──→ [ addr | addr | addr | ... ] ──→ data blocks
│
├── Double indirect   ──→ [ ptr | ptr | ptr | ... ]
│                                ↓
│                         [ addr | addr | ... ] ──→ data blocks
│
└── Triple indirect   ──→ [ ptr | ptr | ptr ]
                                ↓
                          [ ptr | ptr | ptr ]
                                ↓
                          [ addr | addr ] ──→ data blocks
```
| Levels | How it Works | Used for |
|---|---|---|
| **Direct** (10 slots) | Address stored directly in the I-node | Small files |
| **Single Indirect**| I-node points to a block of addresses | Medium files|
| Double Indirect | I-node points to a block of pointers to single Indirect blocks | Large files |
| Triple Indirect | Three levels deep | Very large files |

#### Key Insights
- **Small files** (the vast marjority) are **fast** - all addresses are in the I-node itself, fetched in one disk read when the file is opened.
- Only large files pay the cost of extra disk reads to follw indect blocks.
- The system scales to very large files without wasting space on small ones.

### Path Resolution - How /usr/ast/mbox Gets Found
The file system has no shortcuts to jump directly to a file from its path. It walks the path one component at a time, each step costing at least one I-node read and one directory read.

#### Step by Step for /usr/ast/mbox
```
Step 1: read root inode          (fixed location on disk)
Step 2: read root directory      (find "usr")
Step 3: read usr inode           (fixed location from inode number)
Step 4: read /usr directory      (find "ast")
Step 5: read ast inode           (fixed location from inode number)
Step 6: read /usr/ast directory  (find "mbox")
Step 7: read mbox inode          (kept in memory until file closed)
Step 8: read mbox data block     (the actual file content)
```

#### Total Disk Operations
```
Root:   [inode read] + [directory read]  = 2 operations  (steps 1 and 2)
/usr:   [inode read] + [directory read]  = 2 operations  (steps 3 and 4)
/ast:   [inode read] + [directory read]  = 2 operations  (steps 5 and 6)
/mbox:  [inode read] + [data block read] = 2 operations  (steps 7 and 8)
________________________________________________________________________
Total   = 8 operations
```
