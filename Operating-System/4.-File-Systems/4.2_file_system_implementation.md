## 4.2.2 File System Layout

### Sector vs Partition vs Block
| Term | Descrition|
|---|---|
| Sector    | Physical unit on the harware. the smallest thing the disk can read/write. |
| Partition | A defined range of sectors the OS treats as one independent region. Think of sectors as individual bricks, while partition is a section of wall built from those bricks|
| Block     | Logical unit used by the file system - a group of sectors. The filesystem works in blocks, while the hardware works in sectors.|

### The Disk Level
- **Sector 0** of the entire disk = MBR (Mater Boot Record)
    - Used to boot the computer.
    - The *end* of the MBR holds the **partition table** - lists the start and end addresses of every partition.
    - One partition is marked **active** (the bootable one)

### Boot Process
1. BIOS reads and executes the MBR.
2. MBR locates the active partition.
3. MBR reads that partition's first block -> **Boot block**.
4. Boot block loads the OS contained in that partition.

### Inside a Parition
Every parition start with a **Boot block**, even if it has no OS - for uniformity and possible future use.

After the boot block, a typical partition layout would look something like this from top to bottom:

```
[ Boot block      ] <- always first
[ Super block     ] <- filesystem metadata
[ Free space mgmt ] <- bitmap or pointer list
[ I-nodes         ] <- one per file, stores metadata
[ Root directory  ] <- top of this partition's tree
[ Files and dirs  ] <- all actual content
```

### Each Section Briefly Explained
### Boot Block
- First block of every partition.
- Contains code to load the OS (if partition is bootable).
- Present even on non-bootable partitions for consistency.

### Superblock
- Holds **key information** about the filesystem.
- Read into memory at boot or when the filesystem is first accessed.
- Typical contents:
    - **Magic numbers** - Identifies the filesystem type.
    - **Number of blocks** in the filesystem

### Free Space Management
- Tracks which blocks are available.
- Two common approaches:
    - Bitmap - a long list of bits, ```1``` = used, ```0``` = free.
    - freelist - a linked list of free block addresses

### I-nodes (Inode Table)
- An array of data structures, one for every file.
- Does **not** store file content, only stires metadata:
    - File Size, owner, permissions, timestamps
    - Pointers to where the actual data blocks are on disk.

### Root Directory
- The top of the file-system tree for this partition.
- Every partition has its own internal root.

### Files and Directories
- The remainder of the disk partition.
- Contains all actual file content and subdirectories.

## 4.2.3 Implementing Files

### Contiguous Allocation
Each file is stored as one unbroken run of consecutive disk blocks. Meaning they are stored right next to each other with little to no room in between.

#### How It Works
- A 50kb file on a disk with 1KB blocks -> get 50 consecutive blocks.
- Files are written one after another from the start of the disk.
- Each file starts at a new block - any leftover space at the end of the last block is wasted.
- Only need to track two numbers per file:
    - The **disk address** of the first block.
    - The **number of blocks** in the file.
    - Any other block = first block + offset (simple addition)

#### Advantages
- Simple to implement - minimal bookeeping (just two numbers per file)
- Execellent read performance - entire file read in one operation, only one seek needed (to the first block), then data flows at full disk speed with no delays.

#### The Big Problem: Fragmentation
- When files are deleted, their blocks are freed -> leaves holes on the disk.
- The disk is **NOT** compacted after deletion, since copying millions of blocks would take hours.
- Over time the disk becomes a mix of files and potentially unusuable holes.
- To place a new file in a hole, you must know the final file size in advance.
- If you **underestimate** -> program terminates early when the hole fills up.
- If you **overestimate** -> no hole large enough exists, file can't be created
- Fustrating experience for users.

> [!Note]
> Contiguous allocation is simple and fast but only practical when file sizes are known upfront. It was used on early magnetic disks, abandoned due to fragmentation issues, then came back for things like CD, DVD, and Blu-ray, where sizes are fixed.

### Linked-List Allocation
Each block of a file will store information about the next block of the file.

#### How It Works
- A pointer takes up the first few bytes in in the block.
- The pointer will point to the location of the next block.

#### Advantages
- No external fragmentation (random holes), but there are still negligible internal fragmentation (wasted space on the last block).

#### The Big Problem
- Random access is very slow. In order to get the nth block, you need to get all the location of the previous n-1 locations.
- The amount of data stored is no longer a power of 2. This may require to read two blocks and merge them manually.

### Linked-List Allocation Using a Table in Memory
Instead of putting the pointer data in a block with the actual file block content, we can keep them seperate. We will store the pointer data in a File Allocation Table (FAT).

#### How It Works
- Each entry represents a physical block.
- In each entry stores the location of the next block.
- The entry with the last block with have a value of -1.

#### Advantages
- Removes the two big problems from the previous linked list design.
- Still need to traverse the table to get the nth block we need to read but generally faster because it in the main memory and no disk read operation is needed.

### The Big Problem
- The entire table must be in the **main memory** at all times for this to work. With 1TB disk and a 1KB block size, the table will need a total of 1 billion entries, each entry will have a minimum of 3 bytes. The total comes out to about 3GB. This means that the table does not scale well with large disks.

### I-nodes
Instead of using a linked list allocation, we can associate each file with a data structure called an I-node.

#### How It Works
- The first thing listed by the I-node are the file attributes.
- The remaining space are for listing the disk addresses of the file's blocks.
- The last disk address is for a block containing more disk addresses in case the file grows.

#### Advantages
- The I-node only needs to be in memory if the corresponding file is open. If each I-node requires **n bytes** and a maximum **k files** can be open at a time, then only **kn bytes** are required.

## 4.2.4 Implementing Directories

### Opening a File
1. User supplies a path name
2. OS uses it to find the directory entry on disk
3. Directory entry provides the location info which depends on the allocation method

| Allocation Method | What the Directory Stores |
|---|---|
| Contiguos    | Disk Address of the entiref file |
| Linked-list  | Address of the first block |
| I-node based | The i-node number |

### Two Seperate Design Problems
| Problem | Question being asked |
|---|---|
| Problem 1| Where should file attributes be stored? |
| Problem 2| How should variable length file names be stored? |

### Storing File Attributes

#### Option 1 - Directly In Directory Entry
- Directory = list of entries, each containing: **file name** + **attributes** + **disk addresses**
- Attributes are fixed sized and sit inside the entry itself
- Simple, but everything is packed into the directory

```
[ file name | attributes | disk addresses ] <- one directory entry
[ file name | attributes | disk addresses ]
```

#### Option 2 - In the I-node
- Directory entry is much shorter: just **file name** + **I-node number**
- Attributes are moved out to the I-node instead

```
Directory entry: [ file name | I-node number ]
                                   |
                                   v
                    I-node: [ attributes | disk addresses]
```

### Storing Variable Length File Names

#### Option 1 - Reserve 255 chars For Every Entry
- Simple to implement.
- Wastes a huge amount of directory space because most names are short.

#### Option 2
- Each entry = **fixed header** + **variable length name**
- Name is terminated by **null** terminating character (```0```).
- Entries are **variable length** overall because the name varies

> [!Note]
> Drawback: Deleting a file leaves a variable sized gap, the next file may not fit. Same fragmentation problem as contiguos dosk allocation (but manageable since directories live in memory).

```
[ entry length | attributes | filename....... | padding]
[ entry length | attributes | filename... | padding ]
```

#### Option 3

- Directory entries are all **fixed length**, names are pushed out to a heap
- Fixed size entries mean a removed entry fits the next file.
- No padding needed - names don't need to align to word boundaries.

```
Directories entries (all same size):
[ attributes | pointer ] -> "project-budget"
[ attributes | pointer ] -> "personnel"
[ attributes | pointer ] -> "foo"

Heap (at end of directory):
[ project-budget | personnel | foo | ... ]
```

> [!Note]
> Drawback: Page faults can still occur when reading the names in either option 2 and 3.


## 4.3.5 Shared Files

Multiple users need to share the same file.How does the filesystem support this without breaking consistency?

### Naive Approach
If directories store disk block addresses firectly, sharing means copying those addresses into both user' directories.

Problem: If one user appends to the file, new blocks are only recorded in their directory. The other user's directory still points to the old blocks, they never see the new data which completely defeats the purpose of sharing.

```
B's directory: [ block 4, block 7 ]           <- stale after C appends
C's directory: [ block 4, block 7, block 12 ] <- updated
```

### Solution 1 - Hard Links

Instead of storing disk addresses in directories, store then in an I-node. Both directories will point to the same I-node.

```
B's directory entry --->
                        |
                        ---> [ I-node (owner: C, count: 2) ] -> disk blocks
                        |
C's directory entry --->
```

- The I-node tracks a **link count**, basically how many directory entries currently points to it.
- Both users always see the same data because they share one I-node.

#### The Deletion Problem with Hard Links
When C (the owner) tries to delete the file:
- The OS cannot just remove the I-node since B still points to it.
- Instead: C's directory entry is removed, link count drops from 2 -> 1
- The I-node stays alive until count reaches 0 (until eveyone removes it)

```
Before :            B ---> I-node (count: 2) <--- C
After C deletes:    B ---> I-node (count: 1)        [C's entry gone, file still exists]
```

#### Awkward Consequence
- C gets billed/charged for a file they already "deleted" until B removed their link too.

### Solution 2 - Soft Links (Symbolic Links)

B gets a special file of type **LINK** in their directory.The file contains just the **path string** to C's file, note that this is not an I-node pointer.

```
B's directory ---> [ LINK file: "/C/project/file.txt" ]
                        |
                        | (OS follows path at access time)
                        v
C's directory ---> [ I-node ] -> disk blocks
```

- Only C (the true owner) has a real I-node pointer
- When B accesses the file, the OS reads the LINK file, parses the path, and finds the I-node.

#### What Happens When C Deletes the File?
- The file and its I-node are destroyed immediately, since only C was pointing to it.
- B's symbolic link becomes a **dead link**, the next access will fail because the path will lead to nowhere.
- Removing B's symbolic link has no effect on the original file itself.

### Comparison
| | Hard Link | Symbolic Link |
|---|---|---|
| What is stored?               | Pointer to I-node             | Path string to file |
| Who has I-node pointer?       | All linked users              | Only the true owner |
| File deleted by Owner         | Stays alive until count = 0   | Destroyed immediately |
| Dangling reference possible?  | No                            | Yes (dead symbolic link) |
| Extra overhead?               | Minimal                       | Yes - path mist be read, parsed and followed every access |
| Works across machine/networks?| No                            | Yes (can include network address) |
| Extra I-node needed?          | No                            | Yes - one per symbolic link |


### Shared File Side Effects - Duplicate Traversal
When links are allowed, a single file can be reached via multiple paths. This causes problems for programs that walk a directory tree:
- A backup program dumping all files to tape may **copy** a linked file **multiple times**.
- If that tape is restored on another machine, the file ends up duplicated on disk instead of being linked.
> [!Note]
> This applies to both hard and symbolic links.

### Why Filesystem Becomes a DAG

Normally a filesystem is a tree (one parent per directory). Once shared files/links exists, a file can have **multiple parents** amking the structure a **Directed Acyclic Graph (DAG)**. This complicates operations like traversal and garbage collection but is necessary consequence of supporting sharing.
